RESUME EXECUTIF - CC APP BACKEND (Monolithe Modulaire)
Date: 07 mars 2026
Branche de travail: dev

1) Vue d'ensemble
- Le projet est un backend fintech construit en Spring Boot (Java 21), organisé en monolithe modulaire.
- Il couvre aujourd'hui les domaines: Identity, Subscription, PSP, Accounting/Reconciliation, Circles.
- Le socle technique est déjà opérationnel en production Docker avec pipeline GitLab CI.
- L'architecture actuelle permet d'ajouter de nouveaux modules sans casser l'existant si on conserve les conventions module par module (controller/service/repository/domain/dto + migration Flyway).

2) Stack et architecture technique
- Framework: Spring Boot 3.5.11
- Langage: Java 21
- Persistence: Spring Data JPA + PostgreSQL
- Migration DB: Flyway
- Sécurité: Spring Security (Bearer + API Key interne)
- Documentation API: springdoc OpenAPI (profil dev)
- Observabilité: Actuator + logback
- Build/packaging: Maven + Docker
- Déploiement: GitLab CI/CD + docker compose (dev/prod)

3) Modules métiers en place

3.1 Identity
- Synchronisation utilisateur via token (Firebase ou mode dev token).
- Création/upsert utilisateur, device, session.
- Onboarding profil utilisateur.
- Consultation du profil courant.
- Gestion sécurité utilisateur: blocage device, rotation refresh token, révocation session.
- Endpoint interne pour bloquer un compte.

3.2 Subscription
- Liste des plans d'abonnement actifs par pays.
- Initiation d'abonnement avec idempotency key.
- Création d'opération de paiement (status INITIATED).
- Liaison avec un PSP reference.

3.3 PSP (Jawupay)
- Callback PSP exposé et protégé par:
  - vérification HMAC,
  - anti-replay (nonce + fenêtre timestamp),
  - rate limit par IP.
- En cas de succès callback: confirmation opération + écriture comptable.
- Note: client PSP actuel encore simulé (stub) pour l'initiation.

3.4 Accounting / Ledger / Reconciliation
- Moteur d'opérations comptables (INITIATED -> CONFIRMED).
- Posting en double entrée (debit/credit équilibré).
- Stockage événements comptables + écritures ledger + snapshots de soldes.
- Import de fichiers de rapprochement PSP.
- Gestion mismatch + génération d'ajustements comptables.
- Synthèse de settlement par devise.

3.5 Circles (nouveau module)
- Création de cercle (le créateur devient COACH automatiquement).
- Adhésion à un cercle actif.
- Consultation du cercle actif de l'utilisateur.
- Listing des membres d'un cercle.
- Journal d'activités de cercle.
- Règles métier appliquées:
  - max 5 membres par cercle,
  - un utilisateur ne peut appartenir qu'à un seul cercle actif.

4) API exposées (principales)
- Identity: /identity/*
- Internal Identity: /internal/identity/*
- Subscription: /subscriptions/*
- PSP: /psp/jawupay/callback
- Reconciliation: /reconciliation/*
- Circles: /circles, /circles/{circleId}/join, /circles/my-circle, /circles/{circleId}/members

5) Base de données et migrations
- Flyway migrations en place:
  - V1: identity
  - V2: accounting + reconciliation
  - V3: subscription plans
  - V4: psp callback events
  - V5: hardening comptable + seed plans
  - V6: circles (circles, circle_members, circle_activity + contraintes)
- Le schéma couvre les besoins métier actuels.
- Des garde-fous BD existent sur certaines règles critiques (append-only, unicité, triggers circles).

6) Sécurité
- Endpoints /internal/* protégés par API key interne.
- Endpoints métiers privés protégés par Bearer.
- Endpoints publics limités (health/info, plans, callback PSP).
- Gestion des sessions et refresh token implémentée.

7) Qualité, tests et exploitation
- Tests unitaires présents sur des services critiques (operation, accounting posting, refresh token).
- Build Maven et tests passent.
- Pipeline CI/CD configuré (scan dépendances, scan secrets, build, push image, déploiement).
- Docker compose dev/prod en place.

8) Risques et points d'attention
- Présence de secrets sensibles dans certaines configurations historiques.
- Mélange de configuration moderne et legacy dans les fichiers properties.
- Faible couverture en tests d'intégration et tests end-to-end (notamment parcours API complet).
- Client PSP d'initiation encore mock/stub.

9) Priorités recommandées (court terme)
1. Sécuriser et externaliser tous les secrets (rotation immédiate).
2. Renforcer tests d'intégration sur flux critiques (identity, subscription, callback PSP, reconciliation, circles).
3. Remplacer le client PSP stub par une intégration réelle robuste (timeout/retry/idempotence).
4. Continuer l'extension modulaire prévue (billing, lifecycle, backoffice, reporting, notification).

Conclusion
- Le projet est déjà structuré, déployable et fonctionnel sur les flux principaux.
- La base technique est solide pour accélérer l'ajout de nouveaux modules.
- Les gains prioritaires attendus sont surtout sur la sécurité opérationnelle, la fiabilité intégration et la couverture de tests.
