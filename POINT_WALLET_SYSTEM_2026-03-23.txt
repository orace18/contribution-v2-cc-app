POINT D'AVANCEMENT - WALLET SYSTEM
Date: 2026-03-23
Scope: verification du code existant par rapport aux 15 exigences wallet/ledger.

Synthese executive
- Le socle wallet business layer est deja bien avance (API wallet, reservations, auto-debit, AML max balance, events, postings ledger dedies).
- Le systeme n'est PAS encore "production-ready complet" au sens de la demande initiale.
- Statut global: PARTIEL (environ 60-70% de la cible fonctionnelle).

Statut par exigence

1) WALLET ARCHITECTURE
Statut: PARTIEL
- OK: separation presente entre wallet metadata (table wallets) et verite financiere ledger (country_chart_accounts + ledger snapshots).
- OK: 1 compte ledger wallet par holder via findOrCreateWallet().
- GAP: "1 wallet metadata ACTIVE obligatoire par account_holder" non garanti strictement.
- GAP: pas de contrainte DB explicite "1 wallet metadata par account_holder" (possible duplication).

2) PHONE-BASED WALLET IDENTITY (1 phone = 1 wallet)
Statut: PARTIEL
- OK: bind sur PhoneVerifiedEvent via WalletPhoneBindingListener.
- OK: unicite DB sur wallets.mobile_money_number.
- GAP: en cas de telephone deja utilise, listener fait un skip + log (pas de rejet explicite cote parcours metier).

3) WALLET BALANCE STRUCTURE
Statut: FAIT
- OK: main_balance derive du ledger snapshot.
- OK: reserved_balance derive de wallet_reservations ACTIVE.
- OK: available_balance = main - reserved.
- OK: aucun stockage direct de available/main dans la table wallet.

4) WALLET PERMISSION SYSTEM
Statut: PARTIEL
- OK: check wallet ACTIVE + check available balance avant debit via WalletGuardService.
- GAP: "no restriction" (blocage reglementaire/suspension) non implemente explicitement.

5) PAYMENT VIA WALLET (/wallet/pay)
Statut: FAIT (coeur)
- OK: endpoint POST /wallet/pay.
- OK: validate balance + operation + double-entry ledger debit/credit.
- OK: idempotency via operations.idempotency_key.

6) FUND RESERVATION SYSTEM
Statut: PARTIEL+
- OK: table wallet_reservations avec wallet_id, amount, reason, expiry_date, status.
- OK: reserved funds non depensables (utilise dans available balance et debit guard).
- OK: reserve/release events emis.
- GAP: expiration auto existe en methode (expireStaleReservations) mais pas de scheduler branche.

7) AUTO-DEBIT TRIGGERS
Statut: FAIT (coeur)
- OK: declenchement sur WALLET_CREDITED.
- OK: execution par priorite (ordre).
- OK: debit auto idempotent par regle + operation source.

8) WALLET LIMIT (AML max_balance)
Statut: FAIT (coeur)
- OK: config par country + kyc + currency.
- OK: blocage si depassement.
- OK: log/trace via wallet_aml_alerts.

9) DEPOSIT SYSTEM (PSP + Agent)
Statut: PARTIEL
- OK: agent cash-in implemente (debit agent wallet / credit user wallet) + trace ledger.
- GAP critique: flow PSP incomplet (initiation wallet deposit cree operation, mais pas d'integration complete JawuPay sur ce flux).
- GAP critique: liaison callback PSP -> confirmation wallet deposit non finalisee dans la chaine existante.

10) WITHDRAWAL SYSTEM (wallet -> JawuPay payout)
Statut: PARTIEL
- OK: endpoint withdraw + KYC gate + debit ledger wallet vers PSP_CLEARING.
- GAP critique: integration payout JawuPay effective non implementee (pas d'appel payout reel dedie).
- GAP: "limits enforced" pour retrait au-dela du simple solde dispo/KYC non explicite.

11) AGENT WALLET (FLOAT)
Statut: PARTIEL
- OK: wallet_type AGENT existe et est utilise pour agent cash-in.
- GAP: pas de workflow complet de provisioning/gestion AGENT wallet (creation lifecycle/limites dediees).

12) LEDGER RULES (double-entry, traceable, no direct update)
Statut: FAIT
- OK: operations wallet passent par Operation + AccountingPostingService.
- OK: double-entry systematique.
- OK: pas de mutation directe de solde wallet.

13) EVENTS
Statut: FAIT
- OK: WALLET_CREDITED, WALLET_DEBITED, WALLET_RESERVED, WALLET_RELEASED emis.

14) REMOVE INVALID LOGIC
Statut: PARTIEL
- OK: checks de balance/reservation presentes sur les debits wallet principaux.
- GAP: manque encore controle "restriction" et certains trous de flux PSP.

15) ACCEPTANCE TESTS DEMANDES
Statut: MANQUANT
- Aucun test wallet dedie trouve couvrant:
  - reserve 3000 sur 10000 puis debit 8000 FAIL / 6000 OK
  - auto-debit apres credit
  - blocage max balance.

Priorites critiques a traiter (ordre recommande)
1. Finaliser PSP wallet deposit et payout withdrawal avec JawuPay (end-to-end, callbacks, statuts).
2. Enforcer strictement "1 wallet metadata ACTIVE par account_holder" + creation auto robuste si absent.
3. Ajouter controle "no restriction" avant debit (blocage metier/compliance).
4. Brancher expiration automatique des reservations (job planifie).
5. Ecrire les tests d'acceptation wallet exiges (scenarios 15) + integration tests API.

Conclusion
La base est solide et bien orientee ledger/business-layer, mais il reste des manques bloquants compliance/production sur les flux PSP, les garde-fous d'unicite/permission et la couverture de tests d'acceptation.
