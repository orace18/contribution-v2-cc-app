1. VUE D'ENSEMBLE DU PROJET
================================================================================

Nom          : CC-APP Backend (Club Chrétien Application)
Type         : Monolithe modulaire fintech
Rôle         : API backend pour application mobile de tontines, microfinance,
               MLM, épargne rotative et financement communautaire
Déploiement  : Dockerisé, derrière API Gateway (api-gateway.clubchretien.org)
Chemin API   : /cc-backend-monolitic/

Le backend est organisé en modules (packages) thématiques, chacun avec ses
propres controllers, services, entités, repositories et DTOs.

3. ARCHITECTURE GÉNÉRALE
================================================================================

Le projet suit une architecture "Modular Monolith" (monolithe modulaire) :
- Un seul déploiement (pas de microservices)
- Modules séparés par domaine métier avec frontières claires
- Communication interne via événements Spring (ApplicationEvent)
- Pas de couplage direct entre modules (via interfaces ou events)

Structure des packages :
  com.ccapp
  ├── admin/           → Back-office administrateur
  ├── identity/        → Identité, authentification, wallets, délégation
  ├── wallet/          → Transactions wallet

  ├── circlesocial/    → Social & engagement dans les cercles
  ├── community/       → Posts, commentaires, chat communautaire
  ├── credit/          → Scoring crédit & prêts internes
  ├── financing/       → Partenaires financiers & dossiers externes
  ├── payments/        → PSP, commissions, abonnements
  ├── mlm/             → Réseau MLM multi-niveau
  ├── capital/         → Pool de capital
  ├── ledger/          → Comptabilité double entrée
  ├── country/         → Configuration multi-pays
  ├── platform/        → Configuration plateforme
  ├── progress/        → Suivi progression utilisateur

5. SÉCURITÉ & AUTHENTIFICATION
================================================================================

Classe principale : com.ccapp.config.SecurityConfig

Le backend utilise 3 mécanismes d'authentification distincts selon le type
de client :

--- 5.1 Firebase Authentication (utilisateurs mobiles) ---

  Filtre  : FirebaseAuthenticationFilter
  Fonctionnement :
    - Le client mobile envoie un token Firebase dans le header Authorization
    - Le filtre valide le token via Firebase Admin SDK
    - Extrait les claims (uid, email, rôles)
    - Crée un SecurityContext Spring pour la requête

  Services :
    - FirebaseTokenVerifier      → vérifie les tokens utilisateurs
    - FirebaseAdminTokenVerifier → vérifie les tokens admin Firebase

--- 5.2 Admin JWT (back-office administrateur) ---

  Filtre  : AdminJwtAuthenticationFilter
  Fonctionnement :
    - Admin se connecte via POST /api/admin/auth/login (email + password)
    - Reçoit un temporaryToken si 2FA requis
    - Valide le code TOTP (Google Authenticator) via POST /api/admin/auth/verify-2fa
    - Reçoit un JWT signé (TTL : 480 min = 8h)
    - Le filtre vérifie ce JWT sur chaque requête admin
    - Extrait le rôle admin du payload JWT

  Service 2FA : TotpService
    - Génère un secret TOTP par admin (stocké en base, hashé)
    - Compatible Google Authenticator / Authy

--- 5.3 API Key (APIs internes et partenaires) ---

  Filtre : ApiKeyAuthenticationFilter
  Fonctionnement :
    - Clé API dans le header X-Api-Key (ou similaire)
    - Utilisé pour les appels internes et les intégrations partenaires

--- 5.4 Rôles admin ---

  ROLE_SUPER_ADMIN    → Accès total, gestion des autres admins
  ROLE_COUNTRY_ADMIN  → Gestion d'un pays spécifique
  ROLE_IMF_ADMIN      → Gestion des IMF/partenaires financiers
  ROLE_OPERATIONS     → Opérations courantes
  ROLE_SUPPORT        → Support client, lecture seule
  INTERNAL            → APIs internes machine-à-machine

--- 5.5 Règles d'accès ---

  - CSRF désactivé (API REST stateless)
  - Sessions : STATELESS (pas de session serveur)
  - CORS configuré pour les origines autorisées
  - Endpoints publics : /public/**, /api/admin/auth/**,
    /psp/jawupay/callback, /ws/**

6. MODULE ADMIN
================================================================================

Package : com.ccapp.admin

Rôle : Fournit tous les endpoints du back-office administrateur pour gérer
la plateforme, les utilisateurs, les finances, les pays, et les admins.

--- 6.1 AdminAuthController ---
  Base URL : /api/admin/auth

  POST /login
    - Body : { email, password }
    - Retourne : { temporaryToken, requiresTwoFactor, requiresTwoFactorSetup }
    - Vérifie les credentials de l'admin en base
    - Si 2FA activé → retourne temporaryToken pour étape suivante

  POST /verify-2fa
    - Body : { temporaryToken, code }
    - Valide le code TOTP de 6 chiffres
    - Retourne le JWT définitif : { token, user }

  POST /setup-2fa
    - Body : { challengeToken, code }
    - Pour les admins qui configurent leur 2FA pour la première fois
    - Retourne : { secret, qrCodeUrl, otpAuthUrl, manualEntryKey }

  POST /accept-invitation
    - Body : { invitationToken, password }
    - Permet à un admin invité de créer son compte
    - Active l'account (status → ACTIVE)

--- 6.2 AdminInvitationController ---
  Base URL : /api/admin/invitations
  Auth requise : Admin JWT
  Note : La plupart des actions nécessitent ROLE_SUPER_ADMIN

  GET /admin-accounts
    - Liste tous les comptes admin existants (AdminAccountSummaryResponse[])
    - Inclut : id, email, role, countryId, countryCode, status, twoFactorEnabled,
               createdAt, activatedAt
    - Accessible à tous les rôles admin

  POST /
    - Body : { email, role, countryId, expiresInHours? }
    - Crée une invitation par email pour un nouvel admin
    - Validation : SUPER_ADMIN sans countryId, autres rôles avec countryId
    - Expire après 72h par défaut
    - Envoie un email d'invitation (AdminInvitationNotifier)
    - Requiert ROLE_SUPER_ADMIN

  GET /
    - Liste toutes les invitations (AdminInvitationResponse[])
    - Inclut : id, email, role, countryId, status (PENDING/ACCEPTED/EXPIRED),
               expiresAt, createdAt

  POST /{id}/resend
    - Renvoie l'email d'invitation (régénère le token)
    - Requiert ROLE_SUPER_ADMIN + invitation PENDING et non expirée

  POST /{id}/revoke
    - Révoque une invitation (status → EXPIRED, expiresAt → maintenant)
    - Ne peut pas révoquer une invitation déjà ACCEPTED
    - Requiert ROLE_SUPER_ADMIN

  POST /admin-accounts/{id}/disable   ← AJOUTÉ (session courante)
    - Désactive un compte admin (status → DISABLED)
    - Erreur si déjà DISABLED
    - Requiert ROLE_SUPER_ADMIN
    - Log audit : DISABLE_ADMIN_ACCOUNT

  POST /admin-accounts/{id}/enable    ← AJOUTÉ (session courante)
    - Réactive un compte admin désactivé (status → ACTIVE)
    - Erreur si status != DISABLED
    - Requiert ROLE_SUPER_ADMIN
    - Log audit : ENABLE_ADMIN_ACCOUNT

  PUT /admin-accounts/{id}/role       ← AJOUTÉ (session courante)
    - Change le rôle d'un admin existant
    - Body : { role, countryId }
    - Validation : SUPER_ADMIN → countryId null, autres → countryId obligatoire
    - Requiert ROLE_SUPER_ADMIN
    - Log audit : CHANGE_ADMIN_ROLE

--- 6.3 AdminUserController ---
  Base URL : /api/admin/users

  GET /
    - Liste tous les utilisateurs de la plateforme
    - Retourne : AdminPlatformUserResponse[] (paginé)

  GET /{accountHolderId}
    - Détail complet d'un utilisateur
    - Inclut : profil, statut KYC, prêts actifs, cercles, wallets

  POST /{accountHolderId}/block
    - Bloque un compte utilisateur
    - Status → BLOCKED, raison : "Blocked by admin back office"

  POST /{accountHolderId}/unblock
    - Débloque un compte utilisateur
    - Status → ACTIVE

--- 6.4 AdminLedgerExplorerController ---
  Base URL : /api/admin/finance

  GET /ledger
    - Explore les écritures comptables avec filtres
    - Params : accountCode?, operationType?, fromDate?, toDate?, page=0, size=20
    - MAX size : 100 entrées par page
    - Requête JPQL avec join fetch sur Event et Operation
    - Fix appliqué : countQuery explicite pour éviter l'erreur 500 sur pagination
      (le join fetch ne peut pas être dans la count query automatique)

--- 6.5 AdminDashboardController ---
  Base URL : /api/admin/dashboard

  GET /
    - Métriques globales de la plateforme :
      nombre d'utilisateurs actifs, volume de transactions,
      cercles actifs, dossiers de financement en attente, etc.

--- 6.6 AdminCircleController ---
  Gestion et surveillance des cercles de tontine :
  - Liste de tous les cercles (avec filtres pays, statut)
  - Détail d'un cercle et de ses membres
  - Actions d'administration sur les cercles

--- 6.7 AdminWalletMonitoringController ---
  Surveillance des wallets et transactions :
  - Volume de transactions par période
  - Alertes AML (anti-blanchiment)
  - Réconciliation des soldes

--- 6.8 AdminMlmMonitoringController ---
  Monitoring du réseau MLM :
  - Santé du réseau, métriques d'activité
  - Volume hebdomadaire par leg
  - Reconstruction du ledger MLM si nécessaire

--- 6.9 AdminCountryConfigController ---
  Configuration par pays :
  - Activation/désactivation de pays
  - Plan comptable par pays
  - Mapping des comptes systèmes

--- 6.10 AdminTreasuryController ---
  Gestion de la trésorerie :
  - Comptes de trésorerie
  - Mouvements de fonds
  - Réconciliation bancaire

--- 6.11 AdminCapitalController ---
  Gestion des pools de capital :
  - Création et suivi des fonds
  - Allocation aux cercles

--- 6.12 AdminLookupController ---
  Données de référence :
  - Types de documents, codes pays, devises, etc.

--- Entités Admin ---

  AdminUser
    - id (UUID, PK)
    - email (VARCHAR 320, UNIQUE)
    - passwordHash (VARCHAR 255)
    - role (AdminRole enum)
    - countryId (UUID, nullable)
    - status (AdminUserStatus : INVITED | ACTIVE | DISABLED)
    - twoFactorEnabled (boolean)
    - twoFactorSecret (VARCHAR 128, nullable)
    - createdAt (OffsetDateTime)
    - activatedAt (OffsetDateTime, nullable)
    - Index : (role, status), (country_id)

  AdminInvitation
    - id (UUID, PK)
    - email (VARCHAR)
    - role (AdminRole)
    - countryId (UUID, nullable)
    - invitationToken (VARCHAR, unique, régénéré à chaque resend)
    - status (AdminInvitationStatus : PENDING | ACCEPTED | EXPIRED)
    - expiresAt (OffsetDateTime)
    - createdAt (OffsetDateTime)

--- Service AdminInvitationService (détail) ---

  createInvitation(request)
    1. Valide le rôle/countryId
    2. Vérifie qu'il n'existe pas déjà un admin ACTIF avec cet email
    3. Expire les invitations PENDING existantes pour cet email
    4. Crée l'invitation avec token sécurisé (SecureRandom, Base64, 32 bytes)
    5. Calcule l'expiration (défaut 72h ou custom)
    6. Envoie l'email (AdminInvitationNotifier)

  disableAccount(id)  ← NOUVEAU
    1. Charge l'AdminUser (NotFoundException si absent)
    2. Vérifie que status != DISABLED (BusinessException sinon)
    3. Met status = DISABLED
    4. Retourne AdminAccountSummaryResponse avec countryCode résolu

  enableAccount(id)  ← NOUVEAU
    1. Charge l'AdminUser (NotFoundException si absent)
    2. Vérifie que status == DISABLED (BusinessException sinon)
    3. Met status = ACTIVE
    4. Retourne AdminAccountSummaryResponse avec countryCode résolu

  changeRole(id, newRole, newCountryId)  ← NOUVEAU
    1. Valide la cohérence rôle/countryId
    2. Charge l'AdminUser (NotFoundException si absent)
    3. Met à jour role et countryId
    4. Retourne AdminAccountSummaryResponse avec countryCode résolu

--- Service AdminAuditService ---
  Enregistre chaque action admin en base :
  logAction(adminUserId, action, resourceType, resourceId, details)
  Exemples : LIST_ADMIN_ACCOUNTS, DISABLE_ADMIN_ACCOUNT, CHANGE_ADMIN_ROLE,
             BLOCK_USER, CREATE_FINANCING_OFFER, etc.

================================================================================

Package : com.ccapp.identity

Rôle : Gestion complète de l'identité utilisateur, de l'onboarding multi-étapes,

--- 7.1 Structure interne ---

--- 7.2 IdentityController ---
  Base URL : /identity

  POST /sync
    - Synchronise l'identité Firebase ↔ base de données
    - Crée AccountHolder + User si premier accès

  GET /me
    - Retourne le profil complet de l'utilisateur connecté

  POST /onboarding + GET /onboarding
    - Démarre / consulte l'état d'onboarding

  PATCH /onboarding/step-1
    - Étape 1 : Nom, prénom, date de naissance, genre

  PATCH /onboarding/step-2
    - Étape 2 : Activité, situation professionnelle

  PATCH /onboarding/step-3
    - Étape 3 : Capital initial, consentement

--- 7.3 AccountHolder (Entité centrale) ---

  Table : account_holders
  Champs :
    - id (UUID, PK)
    - firstName (VARCHAR)
    - lastName (VARCHAR)
    - phoneNumber (VARCHAR)
    - countryCode (VARCHAR)
    - serviceCountryCode (VARCHAR)
    - accountType (AccountType : STANDARD | MERCHANT | AGENT | IMF)
    - kycStatus (KycStatus : NOT_STARTED | IN_PROGRESS | VERIFIED | REJECTED)
    - kycVerifiedAt (OffsetDateTime, nullable)
    - createdAt (OffsetDateTime)

--- 7.4 Délégation de compte ---

  AccountDelegation
    - Relation parent-enfant entre comptes (famille, tuteur)
    - Rôles : PARENT, CHILD, GUARDIAN
    - Statuts : ACTIVE, SUSPENDED, REVOKED
    - Permet à un parent de gérer le compte d'un enfant

  DelegatedAction
    - Traçabilité des actions effectuées par délégation
    - Types : TRANSACTION, LOAN_APPLICATION, etc.
    - Niveaux de permission : READ, WRITE, EXECUTE

  AssistedMemberVerification
    - Vérification des membres assistés (agents terrain)
    - Types : PHONE, BIO, DOCUMENT

--- 7.5 Vérification téléphone ---

  PhoneVerification
    - Code OTP 6 chiffres
    - TTL : 300 secondes (5 min)
    - Canaux : SMS, WHATSAPP, VOICE
    - Statuts : PENDING, VERIFIED, FAILED, EXPIRED

  Service PhoneVerificationService :
    1. Génère code aléatoire (length configurable)
    2. Envoie via Africa's Talking (SMS ou WhatsApp)
    3. Valide le code soumis
    4. Expire automatiquement après TTL

8. MODULE WALLET
================================================================================

Package : com.ccapp.wallet

Rôle : Opérations financières sur les wallets utilisateurs (solde, paiement,
dépôt, retrait, réservation de fonds, PIN de sécurité).

--- 8.1 WalletController ---
  Base URL : /wallet
  Auth : Firebase JWT

  GET /balance?currency=XOF
    - Calcule le solde réel depuis le ledger comptable
    - Retourne : { available, reserved, currency }

  POST /pin
    - Configure ou modifie le PIN de sécurité
    - Body : { currentPin?, newPin, confirmPin }

  POST /pay
    - Paiement P2P wallet-à-wallet par numéro de téléphone
    - Body : { recipientPhone, amount, currency, description, pin }
    - Flux : validate PIN → check AML limits → debit ledger → credit dest → notify

  POST /deposit/psp
    - Initie un dépôt via PSP (Jawupay)
    - Body : { amount, currency, pspReference }

  POST /withdraw
    - Retrait vers mobile money
    - Body : { amount, currency, mobileMoneyNumber, pin }

  POST /reserve
    - Réserve des fonds (avant confirmation d'une transaction)
    - Body : { amount, currency, reference }

--- 8.2 Entité Wallet ---
  Table : wallets
  Champs :
    - id (UUID, PK)
    - accountHolderId (UUID, FK)
    - mobileMoneyNumber (VARCHAR)
    - currency (VARCHAR 3)
    - status (WalletStatus : ACTIVE | FROZEN | CLOSED)
    - createdAt (OffsetDateTime)

--- 8.3 Services Wallet ---

  WalletBalanceService
    - Calcule le solde depuis le ledger (somme CREDIT - DEBIT)
    - Séparation solde disponible / solde réservé

  WalletPaymentService
    - Vérifie le PIN via WalletSecurityService
    - Vérifie les limites AML via WalletLimitService
    - Effectue le débit via WalletDebitFacade
    - Poste au ledger comptable
    - Publie un événement de notification

  WalletDepositService
    - Traite les callbacks PSP
    - Crédite le wallet via le ledger

  WalletWithdrawalService
    - Vérifie les fonds disponibles
    - Initie le virement mobile money
    - Débite le wallet via le ledger

  WalletGuardService
    - Règles métier : montant min/max, devises autorisées, limites journalières

  WalletLimitService
    - Contrôles AML (anti-blanchiment)
    - Limites configurées par pays

9. MODULE CIRCLES (TONTINES)
================================================================================

Package : com.ccapp.circles

Rôle : Gestion complète des cercles d'épargne rotative (ROSCA - Rotating Savings
and Credit Associations), aussi appelés "tontines".

--- 9.1 CircleController ---
  Base URL : /circles
  Auth : Firebase JWT

  POST /
    - Crée un nouveau cercle
    - Body : { name, countryCode, configSnapshot }

  GET /
    - Liste les cercles de l'utilisateur connecté

  GET /my-circle
    - Retourne le cercle actif principal de l'utilisateur

  POST /{circleId}/join
    - Rejoint un cercle (via code d'invitation ou lien)

  GET /{circleId}/members
    - Liste les membres du cercle

  GET /{circleId}/members/{memberId}
    - Profil détaillé d'un membre

  GET /{circleId}/members/{memberId}/financials
    - Situation financière d'un membre dans le cercle

  GET /{circleId}/members/{memberId}/history
    - Historique des transactions d'un membre

  POST /{circleId}/members/{memberId}/interactions
    - Enregistre une interaction sociale (encouragement, soutien, préoccupation)

--- 9.2 CircleFinanceController ---

  POST /circles/{circleId}/cycles
    - Crée un nouveau cycle de cotisation
    - Body : CreateCircleCycleRequest

  GET /circles/{circleId}/cycles
    - Liste les cycles d'un cercle

  POST /circles/{circleId}/loans
    - Crée un prêt intra-cercle
    - Body : CreateCircleLoanRequest

--- 9.3 CircleInviteController ---

  POST /circles/{circleId}/invites
    - Génère un lien/code d'invitation
    - TTL : 72h par défaut (configurable)

--- 9.4 CircleLoanRepaymentController ---

  POST /circles/{circleId}/loans/{loanId}/repayments
    - Enregistre un remboursement de prêt
    - Met à jour le statut du prêt si entièrement remboursé

--- 9.5 Entités Circles ---

  Circle
    - id, name, coachId (UUID du coach/animateur), countryCode
    - configSnapshot (JSON, version figée de la config au moment de création)
    - configVersion (INT)
    - status (CircleStatus : ACTIVE | PAUSED | COMPLETED | CANCELLED)
    - createdAt

  CircleMember
    - id, circleId, accountHolderId
    - role (CircleMemberRole : COACH | MEMBER | ASSISTED_MEMBER)
    - joinedAt, leftAt

  CircleContribution
    - id, circleId, memberId, cycleId
    - amount, currency
    - status (PENDING | PAID | MISSED | WAIVED)
    - dueDate, paidAt

  CircleCycle
    - id, circleId, cycleNumber
    - startDate, endDate
    - status (ACTIVE | COMPLETED)
    - beneficiaryMemberId (qui reçoit la collecte ce cycle)

  CircleLoan

19. MODULE LEDGER (COMPTABILITÉ)
================================================================================

Package : com.ccapp.ledger

Rôle : Comptabilité en partie double (double-entry accounting). Toutes les
transactions financières de la plateforme sont enregistrées ici.

--- 19.1 Principe ---

  Chaque opération financière génère :
    1. Un AccountingEvent (source)
    2. Deux LedgerEntry minimum (débit + crédit) équilibrées

--- 19.2 Entités ---

  AccountingEvent
    - id, type (PAYMENT | DEPOSIT | WITHDRAWAL | COMMISSION | ADJUSTMENT)
    - operationId (lien vers Operation)
    - postedAt (date comptable)
    - description

  LedgerEntry
    - id, eventId (FK → AccountingEvent)
    - accountCode (code du compte comptable)
    - entryType (DEBIT | CREDIT)
    - amount, currency
    - description
    - lineNo (numéro de ligne pour tri déterministe)
    - createdAt

  AccountBalanceSnapshot
    - Snapshot périodique des soldes par compte
    - Utilisé pour accélérer les calculs de solde

--- 19.3 LedgerEntryRepository ---

  findByAccountCodeOrderByCreatedAtAsc(accountCode)
    → Toutes les écritures d'un compte, chronologique

  findByAccountCodeAndCurrencyOrderByCreatedAtAsc(accountCode, currency)
    → Filtrées par devise

  searchExplorer(accountCode, operationType, fromDate, toDate, pageable)
    → Recherche admin avec join fetch sur Event et Operation
    → Fix appliqué : countQuery séparé sans "join fetch" pour éviter l'erreur
      Hibernate avec la pagination (la count query auto-dérivée avec join fetch
      est invalide et causait une erreur 500 sur /admin/finance/ledger)

--- 19.4 AccountingPostingService ---

  Méthode principale : postTransaction(event, entries[])
    1. Vérifie l'équilibre DEBIT = CREDIT
    2. Sauvegarde l'AccountingEvent
    3. Sauvegarde toutes les LedgerEntry
    4. Met à jour les snapshots de solde

--- 19.5 Module Réconciliation ---

  ReconciliationController → /reconciliation
  ReconciliationRecord     → Enregistrements de réconciliation bancaire/PSP
  ReconciliationService    → Processus de rapprochement

Rôle : Utilitaires et composants partagés entre tous les modules.

--- 28.1 Réponses API standardisées ---

  CommonResponse<T>
    - Enveloppe toutes les réponses API
    - Champs : success (boolean), message (String), data (T),
               timestamp (OffsetDateTime)
    - Factory methods : success(message, data), error(message)

  PageResponse<T>
    - Réponse paginée
    - Champs : content (List<T>), page, size, totalElements,
               totalPages, hasNext

--- 28.2 Exceptions ---

  BusinessException      → 400 Bad Request (règle métier violée)
  NotFoundException      → 404 Not Found (ressource introuvable)
  ConflictException      → 409 Conflict (doublon, état incohérent)
  UnauthorizedException  → 401 Unauthorized (accès refusé)

  GlobalExceptionHandler → gère toutes ces exceptions + catch-all 500

--- 28.3 Système d'événements ---

  DomainEvent → classe de base pour tous les événements métier
  DomainEventPublisher → interface de publication
  SpringDomainEventPublisher → implémentation via ApplicationEventPublisher
  IdempotentEventListenerExecutor → garantit l'idempotence des listeners
  EventListenerCheckpoint → trace les événements déjà traités

--- 28.4 Sécurité ---

  SecurityUtils → récupère l'AccountHolder/User courant depuis le SecurityContext
  AdminSecurityUtils → récupère l'AdminUser courant + son rôle
  AuthenticatedPrincipal → représentation du principal authentifié

--- 28.5 Entité de base ---

  AuditableEntity (base class pour les entités)
    - createdAt (OffsetDateTime, @PrePersist)
    - updatedAt (OffsetDateTime, @PreUpdate)
    - createdBy, updatedBy (nullable, UUID)

--- 28.6 Observabilité ---

  Tracing HTTP : log des requêtes/réponses (configurable)
  Payload max-length configurable
  Auth tokens masqués dans les logs

30. JOBS PLANIFIÉS (SCHEDULED JOBS)
================================================================================

  1. WeeklyGroupBonusJob
     Cron     : 0 55 23 * * SUN (dimanche 23h55)
     Fuseau   : Africa/Porto-Novo
     Action   : Calcule les bonus MLM hebdomadaires et crée les commissions

  2. MlmWeeklySnapshotJob
     Cron     : 0 59 23 * * SUN (dimanche 23h59)
     Action   : Génère les snapshots hebdomadaires MLM

  3. MlmLedgerRebuildJob
     Cron     : 0 */2 * * * * (toutes les 2 minutes, configurable)
     Prop     : mlm.ledger-rebuild.cron
     Action   : Vérifie et corrige les incohérences du ledger MLM

  4. SubscriptionExpirationJob
     Action   : Notifie les utilisateurs dont l'abonnement expire prochainement

  5. AdminInvitationExpiryJob
     Action   : Expire les invitations admin dont la date est dépassée
     Méthode  : AdminInvitationService.expireOutdatedInvitations()

31. FLUX MÉTIER PRINCIPAUX
================================================================================

--- Flux 1 : Inscription et onboarding utilisateur ---

  1. L'utilisateur s'inscrit via Firebase Auth (app mobile)
  2. L'app appelle POST /identity/sync avec le token Firebase
  3. Le backend crée un AccountHolder + un User en base
  4. L'AccountHolder est placé dans le réseau MLM (MLMPlacementService)
  5. Les tâches d'onboarding sont créées (AccountHolderCreatedEvent → progress)
  6. L'utilisateur complète l'onboarding en 3 étapes (PATCH /identity/onboarding/step-*)
  7. La vérification téléphone est déclenchée (OTP SMS/WhatsApp)
  8. Le wallet est activé après vérification
  9. Les documents KYC sont uploadés via POST /kyc/documents
  10. Un admin vérifie les documents et change kycStatus → VERIFIED

--- Flux 2 : Tontine (Cercle) ---

  1. Un coach crée un cercle (POST /circles)
  2. Invite des membres (POST /circles/{id}/invites → lien partageable)
  3. Les membres rejoignent (POST /circles/{id}/join)
  4. Le coach crée un cycle de cotisation (POST /circles/{id}/cycles)
  5. Chaque membre effectue sa cotisation via le wallet
  6. Le bénéficiaire du cycle reçoit le paquot (WalletPaymentService)
  7. Le cycle est clôturé, le suivant commence
  8. Des prêts intra-cercle peuvent être octroyés (POST /circles/{id}/loans)
  9. Les remboursements sont trackés (POST /circles/{id}/loans/{id}/repayments)
  10. À la clôture du prêt : LoanRepaidEvent → notifications + score crédit

--- Flux 3 : MLM et commissions ---

  1. Nouvel utilisateur → placement dans l'arbre MLM (parent = sponsor)
  2. Chaque transaction qualifiante met à jour MlmVolumeLedger
  3. MlmVolumeUpdatedEvent est publié
  4. Chaque dimanche 23h55 : WeeklyGroupBonusJob calcule les bonus
  5. CommissionGeneratedEvent est publié pour chaque bénéficiaire
  6. Un batch de paiement est créé (CommissionPayoutBatch)
  7. CommissionPayoutBatchProcessor crédite les wallets
  8. BonusPaidEvent → notification aux bénéficiaires

--- Flux 4 : Scoring crédit et dossier de financement ---

  1. L'app appelle GET /credit/eligibility
  2. CreditScoringService calcule un score composite (5 facteurs)
  3. L'utilisateur choisit une offre (GET /api/admin/offers)
  4. Soumet une demande (POST /financing/applications)
  5. Uploade les documents requis (POST /kyc/documents)
  6. Un admin examine le dossier (PUT /api/admin/financing/applications/{id}/review)
  7. Si approuvé : le partenaire est notifié, le montant est versé
  8. L'utilisateur rembourse selon l'échéancier
  9. À la clôture : LoanRepaidEvent

--- Flux 5 : Paiement wallet P2P ---

  1. POST /wallet/pay avec { recipientPhone, amount, pin }
  2. WalletSecurityService.validatePin() → vérifie le PIN hashé
  3. WalletGuardService → vérifie montant min/max, devises autorisées
  4. WalletLimitService → vérifie les limites AML journalières/mensuelles
  5. WalletDebitFacade.debit() → débite le compte source
  6. AccountingPostingService.postTransaction() → écrit dans le ledger
  7. WalletDebitFacade.credit() → crédite le compte destinataire
  8. NotificationRequestedEvent → notification à l'envoyeur et au receveur

--- Flux 6 : Callback PSP (dépôt) ---

  1. Jawupay appelle POST /psp/jawupay/callback
  2. Validation HMAC de la signature
  3. Rate limiting (SimpleRateLimiter)
  4. JawupayService traite le type d'événement
  5. Si dépôt confirmé : WalletDepositService.confirmDeposit()
  6. Écriture au ledger + notification utilisateur
